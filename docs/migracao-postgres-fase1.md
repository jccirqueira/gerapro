## 3. Regras de tradução aplicadas

| SQLite | PostgreSQL | Ocorrências |
|---|---|---|
| `TEXT` | `TEXT` | 724 |
| `REAL` | `DOUBLE PRECISION` | 88 |
| `INTEGER` / `INT` | `BIGINT` (int64 do SQLite) | 45 |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 1 (`price_history`) |
| FK inline (`REFERENCES …` na coluna) e FK de tabela | removidas do `CREATE` + `ALTER TABLE … ADD FOREIGN KEY` | 5 |
| Identificadores (`user`, `to`, `from`, `default`…) | **todos citados** (`"user"`) — são palavras reservadas no PG | — |
| Tabelas internas `sqlite_stat1`, `sqlite_sequence` | excluídas (gerenciadas pelo próprio SQLite) | 2 |
| `CREATE INDEX` | sintaxe idêntica (só citar nomes) | 53 |

**Descobertas úteis:**
- **Nenhuma** coluna `BOOLEAN` nativa — flags são `INTEGER 0/1` (→ `bigint`).
  *Decisão "BOOLEAN vs 0/1" ficou resolvida sem mudança de código.*
- **Nenhuma** coluna `BLOB`, nenhum `datetime('now')`, `strftime`, `GROUP_CONCAT`
  ou `json_extract` — a superfície de dialeto é pequena.
- Datas são `TEXT` (ISO) — **não mudam** no PostgreSQL.
- `DEFAULT ''`, `DEFAULT 0`, `DEFAULT 1.65`, `NOT NULL DEFAULT 'default'` — todos válidos no PG.

## 5. Plano das próximas fases

### F2 — Driver + assíncrono (o maior trabalho)
- [ ] Instalar `pg` nas dependências; criar pool de conexão (lê `.env`: host/port/user/pass/db).
- [ ] Reescrever `js/db.js` (3.111 linhas, **70 funções**): `DatabaseSync` → `pg`,
      todos os métodos `async` (`getDb`, `withTransaction`, CRUD genérico, `getFullSync`…).
- [ ] Adicionar `await` nas **135 chamadas** `.prepare()` (120 em `db.js` + 15 em `server_new.js`).
- [ ] Manter contrato público idêntico (mesmos nomes/retornos) — zero mudança nos módulos de negócio.

### F3 — Dialeto SQL
- [ ] Parâmetros `?` → `$1…$n` (135 consultas).
- [ ] `INSERT OR REPLACE` → `INSERT … ON CONFLICT … DO UPDATE` (15).
- [ ] `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING` (4).
- [ ] Substituir o `initSchema()` do `db.js` pelo `postgres-schema.sql` (ou gerá-lo do mesmo fonte).
- [ ] `db.getDb()` exposto no server → encapsular (não vazar driver cru).

### F4 — Migração dos dados
- [ ] Exportar SQLite (por tabela, tipo-aware) → importar via `COPY` no PG.
- [ ] Ajustar sequence do `price_history.id` (`setval`) após importar.
- [ ] Preservar `NULL` × `0` (lição do `materiais.cbs`) e `DEFAULT ''`.
- [ ] Contagens por tabela antes/depois (baseline da seção 4).

### F5 — Validação
- [ ] Paridade de linhas (25.677) e somas de conferência (ex.: `SUM(custo)` de materiais).
- [ ] Âncoras reais: `settings` (CBS 11,2 / IBS 0,1), `PRJ-0001`, PTC `PT-51001002`, materiais com `cbs`.
- [ ] Mesmo cálculo → mesmo preço (precificação e DRE comparadas).
- [ ] Bateria de URLs + fluxos no browser (login, sync, compras/XML, exportações).
- [ ] Carga de concorrência (2+ sessões salvando ao mesmo tempo).

### F6 — Cutover com rollback
- [ ] Subir container `postgres` na VPS (padrão já usado: `barbearia-db`, `prevdrive-db`).
- [ ] Janela curta: parar escritas → delta final → trocar `.env` → restart.
- [ ] **Rollback:** o `gerapro.db` não é apagado — reverter `.env` volta ao SQLite no mesmo minuto.
- [ ] Backup automático: cron `pg_dump -Fc` + cópia **para fora da VPS** (off-site).
- [ ] Manter SQLite como fallback por ~30 dias após estabilidade.

## 6. Riscos conhecidos

| Risco | Mitigação |
|---|---|
| `await` esquecido em ponto de chamada | Lint/`--unhandled-rejections` + bateria F5; o contrato de retorno é verificado por tabela |
| Transações (`withTransaction`) mudam de sync p/ async | Revisar cada uso (padrão: callbacks aninhados → `try/await`) |
| Sequence do `price_history` zerada após import | `setval` obrigatório em F4 |
| Performance do `pg` (round-trip de rede) | Mesma rede Docker na VPS — latência ~0,1 ms; pool de conexões |
| Divergência de comportamento (`''` vs `NULL`, tipagem estrita) | Validação F5 com âncoras + somas de conferência |
